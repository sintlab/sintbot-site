Latest release: 1.4.31 ↓

2026-11-20

1.4.31 · A calmer console

Add a group project and Add model: quieter buttons
The buttons at the top right of Groups · Projects and Models now use a thin outline with a plus sign and are named Add a group project and Add model. When you pick a group that is already bound in the dialog, the title changes to Edit a group project.
An add tile when a list is empty
With no group projects or models yet, the list shows a dashed add tile that opens the matching dialog.
The version number opens Software updates
Click the version number at the top left to go straight to the Settings → Software updates card.
One General card in Settings
Interface language, bot and network, run limits and access addresses are now one General card, collapsed by default; when collapsed it shows the language, the concurrency cap, whether a proxy is set and who can reach the console. The separate Interface card is gone.

2026-11-20

1.4.30 · Fewer held groups, models chosen per group, a tidier console

A start that fails at once no longer holds the group
When Claude Code, or Codex in a group with Add follow-up messages to the current task turned off, reports an error before it starts on a message (for example the usage limit is reached, the sign-in has expired, the previous session cannot be resumed, the chosen model is not available, or the model service cannot be reached), the message is closed as not handled: the conversation is told why and asked to send it again later, and the group keeps handling new messages. Before, this held the whole group, and later messages only got a notice that the last task's result was unknown, without the reason. When the session cannot be resumed, the next message starts a new one; when Codex fails before it starts, the service log says what it printed (with secrets masked). Exceptions: within 90 seconds after an upgrade switches over (while it can still roll back to the previous release), or when the turn combined several messages, the group is still held as before. Codex groups with Add follow-up messages to the current task turned on (the default) keep the previous behaviour in this release.
A message cut off by a crash is reported, not redone, and the group is not held
When the service exits on an error nothing caught, the message it was working on gets a note in its conversation after the restart saying it was not finished (with who sent it and how it began); it is not redone and the group is not held. The session is kept, and its next turn tells the model not to continue that request unless you ask again. The group is still held when the turn combined several messages, more messages were waiting in that conversation, the executor had not yet confirmed it started, or the final reply had begun, and for a turn cut off by stopping the service yourself or by an upgrade restart.
Sealing a held group is no longer blocked by its own task
When you seal a held group from Needs attention in the console, that group's own stuck turn no longer counts as another group's task, so the seal goes ahead; it still waits while other groups are running or have messages queued. Before, a group stuck after its usage limit was reached could be refused because other groups still had tasks, and had to be sealed from the command line with the service stopped.
A tidier console
On the settings page, the Feishu, WeCom and Slack cards fold to one row by default (icon, name, status dot and a short summary); open one for the details, and its dot turns red when the connection fails. The interface language moves from the sidebar to a new Interface card at the top of the settings page. Version history is no longer kept in the console: Release notes → at the bottom of the Software updates card, the version badge next to the brand and the upgrade announcement in groups all link to that version's section of the release notes on the website. Chinese text left on the English interface is now in English.
Models chosen per group; adding a model starts with the key
Model cards that use an API key now work like subscription cards: each group picks its model on its card under Groups · Projects or with /model, and once the card has a key, the list shows the models the provider offers right now; a group that has not chosen runs the model stored on the card. Add model asks for the API key right after the preset, and Verify key runs a short trial on the spot and says why it failed (for example the key was refused, or the endpoint does not speak the Anthropic format); the endpoint, small model, default thinking depth and the rest move under Advanced. A custom endpoint still takes its endpoint and model on the card, shared by its groups.
Model presets
The preset list changes: the GLM preset moves to glm-5.3, Kimi is added and Volcano Ark is removed; the default models of the DeepSeek and MiniMax presets follow the providers' current docs as well. The MiniMax preset uses MiniMax's current endpoint, api.minimax.cn. Model cards and presets show the provider's small logo, the two subscription presets (Claude subscription and GPT via Codex) come first, and the terminal wizard's providers change to match. Existing model cards, including Volcano Ark cards and cards on the old MiniMax endpoint, are not affected and can still be used and edited.
Check and upgrade Claude Code
The Claude subscription model card shows the version of the Claude Code program on this Mac and, when a newer one exists, upgrades it after you confirm: a copy installed with npm is reinstalled with npm, one from the native installer uses its own updater, and any other install is left for a manual upgrade. It will not upgrade while a group is running or queuing a Claude Code task, and every attempt is recorded in the audit log; groups that use Claude Code run the new version from their next turn.
The installer points to Slack first
After the one-line install, the closing message links to connecting your project in Slack first, then notes that Feishu and WeCom are supported too, with their links.

2026-11-19

1.4.29 · Scheduled tasks, and a clean exit on crashes

Scheduled tasks
Create, edit, pause and delete them on a conversation's console card under More settings → Scheduled tasks. There are three kinds: Model (at the time, a line marked [Scheduled] is posted and then handled like an ordinary message), Message (posts the text only) and Script (runs a command in the project folder without the model, and posts one line if it fails or times out). The time can be a cron expression, an alias such as @daily, a shorthand such as 每天 09:00, or one date and time; each task can have its own time zone. Each due time fires at most once; runs missed while the service was down, or reached more than two minutes late, are not made up; failed runs and runs with an unknown result are not retried. In this release tasks are created and changed only in the console, and WeCom conversations do not have them yet.
A clean exit on crashes
When the service hits an error nothing caught, it logs the time and stack trace, stops scheduled tasks and running executors, releases its lock and removes temporary files, then exits with code 1 so the system starts it again; the cleanup waits at most 20 seconds. Before, it exited on the spot and Codex or Claude Code child processes could keep running in the background. The interrupted turn is still treated as having an unknown result after the restart.
Stricter proxy addresses
In Slack setup and settings, the proxy host must be an IP address or a host name in plain ASCII: names in other scripts, labels starting with xn--, and full-width dots and digits are refused; IPv6 addresses in brackets are checked by the standard rules. Before, some of these could be saved and only failed with a different error when connecting.
Slack and console fixes
In Slack, ⚠️ on a held conversation is no longer skipped when checking sealed records fails, and the failure is written to the service log; the log line for another machine connected to the same Slack app is worded more precisely. The busy follow-up switch in the console has English text: Add follow-up messages to the current task.

2026-11-19

1.4.28 · Slack speaks English, stopping inside a thread, a full queue no longer holds the group

A full queue asks you to resend instead of holding the group
When two messages are already waiting, a new one is not handled: the bot asks you to send it again after the current task, and the running task is not affected. Before, in Feishu, WeCom and direct messages this interrupted the current task and held the whole group. A message that arrives while the current task is wrapping up is also answered with a request to resend.
Slack speaks English by default
In Slack, the bot's notices, command replies, status and errors are in English, and the model is asked to answer in English (it still follows a member who writes in another language). Slack conversations that are already connected switch to English after the upgrade; for Chinese, change it on the conversation's console card under More settings → Notice language. Feishu, WeCom and local conversations are unchanged.
Threads in a Slack channel are handled separately
A new @mention in the channel while a task is running no longer joins that task: it waits its turn, runs on its own and is answered in its own thread. Only a reply in the running task's thread is added to it. Replying !stop in a thread stops only that thread's task and the queue carries on; a new @bot !stop in the channel, or /sint stop, still stops the current task and clears the queue.
Unfinished Slack messages are marked
After the service is killed or a conversation is sealed, messages that did not finish get ⚠️ and a single note asking you to send them again if you still need them. Deleting a queued message that has replies now cancels it as well, and several problems when the connection is renewed are fixed.
Slack setup: proxy, Agent option and hints
The Slack step of the setup page fills in a terminal proxy it detects (http only); it is saved as the network proxy of the whole service, so other platforms and the local model tools use it too. Declaring the app as a Slack Agent is optional and off by default. When the bot is not in a channel, it says to /invite it first; when another machine is connected to the same Slack app, the console warns about it.
Wording for direct messages and one-to-one chats
Help, status and notices name the kind of conversation: "this direct message" or "this channel" in Slack. In WeCom a one-to-one chat is no longer called a group, and its project note no longer tells you to mention the bot in a group.
Console fixes
After a failed Codex upgrade the button comes back and the reason stays (local paths are masked); when a model card points to a Codex program other than the one on the PATH, the console asks for a manual upgrade instead. The number of tasks that run at once is checked against 1–32, and changing it while the service runs explains that the configuration file must be edited and the service restarted.

2026-11-18

1.4.26 · Codex upgrades in the console, configuration history and stability

Upgrade Codex and refresh models from the console
After a model card confirms the sign-in, the model list is read again and the card says which models were added or removed; /model in a group waits for the new list (up to 8 seconds). The Codex model card shows the version of the Codex program on this Mac and, when a newer one exists and it was installed globally with npm, upgrades it in one click. It will not upgrade while a group is running a Codex task.
Configuration history and restore
The service stores a copy of the configuration when it starts and after every change in the console, keeping the latest 50. sintbot config history lists which settings each copy changed, never their values; sintbot config restore <version> puts one back while the service is stopped.
Steadier
A malformed request address no longer stops the service; a Feishu request that gets no answer for 30 seconds is abandoned instead of holding the group; previews check where a file really is before serving it; a queued message reads the group's current settings when it starts; the console accepts only sensible concurrency and turn-time values; password-free access is given only to local requests that do not come through a reverse proxy.
Follow-ups that cite the last reply after an idle compaction (experimental)
When Claude Code compacts its context while idle, the next turn carries the reply that was already sent, so a group message such as "1 and 3" still lands on the right items. It is kept in memory only and is gone after a restart.

1.4.21 · Fast for GPT groups; held groups handled in the console

Fast per GPT group
Codex models gain a Speed option: Standard or Fast. Turn it on from the console group card, with /model fast in the group (/model standard to go back) or on the /model card. Changing only the speed keeps the session, works while a task is running and applies from the next message. Off by default; remembered per group and per model card; scheduled tasks always run at standard speed. It cannot be enabled for a model without a Fast tier, and switching to such a model returns to Standard with a note. The receipt states the cost: about 1.5–2x speed, quota charged at 2.5x.
Standard speed is now stated explicitly
Every turn explicitly requests Standard unless the group enables Fast. When App Server reports a fallback, the card footer omits Fast. Older executors and the exec route do not report the effective tier, so their requested tier is not proof of acceleration.
Seal a held group from the console
When the service is killed during a task (power loss, forced restart) and every group is held, the service still starts and the console stays available. The overview's Needs attention card and the local conversation page offer Seal and continue: the record is archived unchanged, that message is not processed again, and the service restarts by itself with a new record. Offered only when running as a managed background service; foreground runs keep the terminal steps in the guide.
No upgrade while the background service is disabled
If the launchd job is disabled in the system (for example under Login Items), a console upgrade is refused with a message instead of leaving the service stopped.
DeepSeek preset
Configure an API Key for DeepSeek Flash and select model and effort per project.
Missing-key preflight
Missing API Keys are rejected before executor startup; keyless cards remain selectable in project settings.

1.4.13 · Reliability and task follow-up improvements

Restore Claude Code health information
Visible Claude Code models show executor version and probe results. Hidden models do not trigger extra probes.
Retry failed upgrades safely
Keep failed installations for inspection. Retry in a separate directory and verify before switching, without overwriting existing installations.
Align runtime version, model and capability information

Continue output after moving a reply card

2026-11-10

1.4.8 · Console interjections, upgrade notices, group messaging skills

Fix: a message sent while the previous reply was still being delivered was refused with "wrapping up, please resend"
A message arriving at the moment a reply, card or the stop confirmation was still on its way to Feishu used to be refused. It now waits for that delivery and is handled in arrival order; a message sent right after /stop is answered normally.
New: the console can post a line into an idle group
A line written in the console is posted to the group as the administrator and handled as an ordinary group message, with the reply in the group. A busy, held or upgrading group is refused with the reason; resubmitting the same line is not processed twice.

On the first start after an upgrade, each serving group receives one card listing what changed. Not sent on a first install or a downgrade; can be turned off in the console.
New: the agent in a group can send messages, notice cards and files, read history, reply, edit and recall
The agent gains group skills: send messages, notice cards, files and images, read the group history, reply to, edit and recall its own messages, download group files and add reactions.

2026-11-09

1.4.7 · /stop no longer pauses the group

Fix: /stop during a task could pause the whole group
/stop removes the task's reply card, and Feishu then reports that removal as a recall. When it arrived while "stopped" was still being sent, it was treated as a fault: the group was paused until an administrator released it, and later /model and /new were refused. The recall now waits for that reply to finish and the group keeps serving.
Fix: recalling a queued message could pause the group
Recalling a message while its "queued" notice was still being sent also paused the whole group; the message is now cancelled once the notice has been sent.

2026-11-09

1.4.6 · A rejected Codex resume no longer holds the group

Fix: a group held when Codex rejected a resume
When Codex refused to continue the previous conversation before doing any work (for example a damaged Codex session history on the machine, or a conversation whose record is gone), the whole group was paused until an administrator released it. Now the group gets one "the last turn did not finish, please send it again" notice, keeps serving, and starts a new conversation, so resending works.
Fix: a queued message stalled the group after a start failure
When the model could not start (program missing or resume rejected), messages queued behind it each get a resend notice; before, the next new message was treated as a busy group and the whole group was paused.

2026-11-09

1.4.5 · Group commands, console settings and Codex sign-in

New /skip in groups
Drops only the current task; queued messages run next and the conversation is kept. /stop still cancels the current task and everything queued.
/help is written for each group
It opens with the group's project and model, lists commands by urgency, describes /skip, /stop and /new in the same terms (what happens to the queue and to the conversation), and explains that recalling your own message cancels it.
New session from the console
An idle group with every record settled starts a new conversation right away; a busy group is told to stop or wait first instead of being reported as reset.
Models can be added and configured from the model cards
No service restart. Changing a model id, backend or endpoint waits for the groups using it to be idle and starts a new conversation for them; the default model and models in use cannot be hidden.
Fix: tool quality and thinking depth settings could not be saved
They were wrongly reported as needing a service restart.
Codex sign-in is checked with the server
The console's Codex model card no longer trusts the local sign-in file alone. It asks the server once with the token and shows one of three states: verified, sign-in expired (run codex login again on this machine), or unverified (the server could not be reached; not treated as signed out). A revoked token no longer keeps showing as signed in.
Fix: stopping a task before it started could swallow the next answer
If the model process failed to start after a console stop or /skip, a stale cancelled flag could silently drop the next task's answer.

1.4.4 · Upgrade progress in the console

Confirm the upgrade in the page
Upgrade now asks for confirmation in the page, stating the versions and that new messages wait about a minute during the switch.
The upgrade window shows each step
Waiting for idle groups, download and install, stopping the current service, checking records and backing up, preflight, switching and starting, and waiting for every group to connect are ticked off one by one with the elapsed time; while waiting it names the groups still working.
Reconnects while the service restarts
During the switch the page says the service is restarting and reconnects by itself; once the new version connects every group it reloads into the new console and shows the result once. A failed step and the restored version are marked.
Can run in the background
Continue in background keeps a spinner on the top-bar icon, which reopens the progress; a notice appears when the upgrade ends.
Takes effect from 1.4.4
The upgrade window comes from the running version: upgrading from 1.4.3 to 1.4.4 still shows the previous screen, and later upgrades show the window.

1.4.3 · Progress on the reply card

A card appears even before any output
If nothing has been produced after 25 seconds, a "Received, working on it" card appears and the answer later replaces it in place. A turn that ends without a reply recalls that card.
The card shows how far the task has got
While running, one line updates every 15 seconds: how long it has run and what it is doing (reading, editing or writing which file, running a command, searching the web; file names only). After 10 minutes it updates once a minute, and notes when nothing has happened for more than 2 minutes. Delivered steps such as writing files, committing or pushing, and sending files to the group are listed with ▶ at the top of the card and fold into a "Process" section when the turn ends.
/status shows progress
While running it shows how many steps have run, how long ago the last activity was, and what it is doing.
Fix: a streamed reply could fail the whole turn
Text that arrived while the previous update was still being sent used to fail the turn; it now queues behind it and keeps updating the card.

1.4.2 · Check and install new versions from the console

Version checks in the console
Software updates in Settings checks for stable releases at startup and daily and shows release notes when a new version is available.
One-click upgrade for background runs
When a launchd agent runs SintBot, Upgrade now waits until every group is idle and settled, installs the new version into its own folder and switches to it; if it does not connect every group within 90 seconds, the previous version is restored. New messages wait about a minute during the switch and are asked to be resent.
Steps for foreground runs
A foreground run shows how to stop, reinstall and start. Upgrades are not announced in groups.

2026-11-09

1.4.1 · A failing group stops only itself

One group's fault leaves the others working
When a group's last task has an outcome that cannot be confirmed (for example a reply whose delivery is unknown, or a runner that exited without a result), only that group is paused; nothing is replayed or retried and the other groups keep working. A paused group answers new messages with a short notice.
One group no longer blocks startup
If a group's records cannot be recovered, the other groups still start and the console marks that group Needs attention. The startup preflight fails and lists such groups.
Incident seal command
Restart first; for a group that is still paused, stop the service and run sintbot incident seal --group <group ID>. The old records are kept unchanged, the group reopens with new records, and messages left unfinished before the seal are not processed again.
